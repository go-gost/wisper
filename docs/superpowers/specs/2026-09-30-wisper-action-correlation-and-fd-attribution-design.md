# wisper: action correlation + tun-fd attribution — design

Status: **approved for implementation** (2026-09-30). Two answers that today each
cost a debugging session: *which UI action caused this backend/p2p log line?* and
*who released the tun device?*

Plan: [docs/superpowers/plans/2026-09-30-wisper-action-correlation-and-fd-attribution.md](../plans/2026-09-30-wisper-action-correlation-and-fd-attribution.md).

## Context (why)

Both came out of the debugging-levers assessment in
[p2p/docs/2026-09-30-p2p-peer-diagnostics-design.md](../../../../p2p/docs/2026-09-30-p2p-peer-diagnostics-design.md)'s
follow-ups, and both were felt while chasing the direct-session churn and the
tun-entrypoint self-close:

- **Who released the device?** Answering it took a `debug.Stack()`: the fd is
  cleared from four places (Kotlin `TunVpnService.establish`/`onStop`/`onRevoke`,
  `WisperService`'s release) and nothing says which one ran.
- **Which action caused this log line?** The mutation middleware logs every
  non-GET request, but nothing joins that line to the *p2p* work the action set
  in motion — the two halves sit in one log stream with no shared key.

## Design

### Action correlation

- The frontend sends **`Wisper-Id: <short random>`** on every request. Not
  `X-`-prefixed (that convention is retired), and it is a **label**: never auth,
  never parsed, never able to change behaviour.
- The backend **generates one when the header is absent** (8 hex chars), so a
  curl, the CLI, or an older bundle is still correlatable. The id is logged on
  the mutation line and put in the request context.
- p2p accepts the id through a **context** — `host.WithAction(ctx, id)`, logged
  as `action=<id>` at the seam calls a caller makes (`Listen`, `Warm`, `Punch`,
  and `Dial`, which already takes a ctx). `endpoint` gains additive ctx variants
  (`ListenContext`, `WarmContext`, `PunchContext`); the existing methods stay
  unchanged, so the third-party API does not break.

**The boundary, stated because it is easy to fake:** correlation reaches the
calls an action *initiates* — the ones on the caller's goroutine. p2p's
background logs (punch rounds, session death, keepalive) stay action-free: one
punch serves every caller, a session outlives any click, and a shared p2p host
serves every tunnel in the process. Tagging those would be a fabricated join,
which is worse than no join.

### tun-fd attribution

Every site that sets or clears the fd logs one line naming *itself*, the fd and
the reason: the Kotlin sites to **logcat** (that is where an adb-side reader
looks) with a fixed tag, and the Go `SetTunFD`/`WaitTunFD` to the wisper log, so
the two timelines can be read together. `onRevoke` in particular says so — a
system revoke and an app-initiated stop must not read alike.

## Decisions

1. **`Wisper-Id`, generated by the backend when missing** — chosen by the user;
   a bare curl and an old bundle must still correlate.
2. **Correlation through the context, at the seam** — no proto change (wisper
   embeds p2p in-process), no global/ambient state, and no faked attributions.
3. **Three ctx variants (`Listen`, `Warm`, `Punch`), not the two first agreed:**
   those are exactly the calls a UI action initiates — `AddForward` is CLI-only
   and has no action behind it. Dropping `PunchContext` is the fallback if the
   smaller surface is preferred.
4. **fd logs on both sides** (Kotlin → logcat, Go → the wisper log): the release
   is decided on the Android side, but the consumer that stops reading is Go.

## Non-goals

- No per-action correlation of background engine logs (see the boundary above).
- No `Wisper-Id` in *auth* or in any decision path — it is untrusted input and
  is treated as a label only.
- No propagation into x/GOST's own logs: the id stops at wisper's boundary, and
  a GOST-side join is a separate question.

## Verifying it

- Unit: an action-carrying ctx logs exactly one `action=` line per seam call and
  a plain call logs none; the middleware generates an id when the header is
  missing and two requests never share one.
- UI: the existing Playwright suite must stay green with the header attached.
- Device (B1): start the tun entrypoint on the real Pixel 9, stop it, and read
  `adb logcat -s wisper-tunfd` — the release names `WisperService`/`TunVpnService`
  and whether it was `onRevoke`.
